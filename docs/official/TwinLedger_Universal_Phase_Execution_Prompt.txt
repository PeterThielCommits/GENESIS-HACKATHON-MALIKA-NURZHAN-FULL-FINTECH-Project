1. ОБЯЗАТЕЛЬНЫЙ КОНТЕКСТ ПРОЕКТА
===============================================================================

TwinLedger — детерминированная синтетическая RL-compatible среда для проверки
ИИ-агентов, выполняющих аудит вымышленных бухгалтерских книг. Генератор создаёт
чистую историю компании и контролируемые аномалии; публичная среда предоставляет
инструменты исследования; независимый verifier проверяет выводимость аномалий
из публичных доказательств; закрытый scorer оценивает findings; harness
изолирует компоненты; arena атакует среду и награду; Judge Kit воспроизводит
проверки и выпускает отчёты.

Ключевые архитектурные принципы, которые нельзя нарушать:
1. Достоверность и проверяемость важнее количества функций и эффекта демо.
2. Truth не вводится произвольно: кандидат truth связан с diff чистого и
   мутированного близнецов, инвариантами и независимой проверкой.
3. Diff подтверждает изменение, но сам по себе НЕ доказывает, что изменение
   семантически является ошибкой.
4. Verifier при обнаружении использует только публичные данные и не импортирует
   генератор, не читает provenance, operator parameters или sealed truth.
5. Environment не получает доступ к truth, provenance, приватным меткам и seed.
6. Policy не должна иметь прямого доступа к памяти scorer или sealed-данным.
7. Каждая аномалия должна быть выводима через доступные policy инструменты.
8. Официальная формула reward и официальный контракт имеют приоритет над
   предварительными предположениями Master ТЗ.
9. Денежные расчёты используют целые minor units и Decimal из строк; float в
   денежных вычислениях запрещён.
10. Детерминизм, replay, контролируемые RNG-потоки и проверяемые receipts.
11. NLP-текст — вспомогательный сигнал, не самостоятельное доказательство.
12. Commit-reveal подтверждает неизменность commitment после публикации, но
   сам по себе не доказывает истинность эталона.
13. Процессная изоляция не должна называться полной OS sandbox, если нужные
   системные ограничения реально не обеспечены.
14. Core должен работать офлайн, в пределах ограничений Master ТЗ и официального
   задания; дополнительные библиотеки не должны случайно становиться
   обязательной зависимостью ядра.
15. Не заявляй о победе, максимальном балле, абсолютной безопасности или
   безошибочности без проверяемых оснований.

План фаз, их точные задачи и EXIT GATE находятся в разделе 24 Master ТЗ.
Приоритеты A/B/C и правила урезания — в соответствующем разделе Master ТЗ.
Не придумывай дополнительные критерии вместо предусмотренных спецификацией.

4. ПЛАН ВЫПОЛНЕНИЯ ВЫБРАННОЙ ФАЗЫ
===============================================================================

После startup-а создай конкретный план реализации. Не ограничивайся общими
фразами вроде «сделать генератор» или «добавить тесты».

Для КАЖДОЙ задачи из выбранной фазы создай таблицу:

| Поле | Что указать |
|------|-------------|
| Phase task | Номер задачи из Master ТЗ, например 8.3 |
| Requirement IDs | Все соответствующие REQ-ID |

| Tests | Какие проверки докажут корректность |

| Owner | Кто отвечает, если команда распределена |
| Dependencies | Что должно быть готово до этой задачи |

Определи минимальную последовательность работ и критический путь. Сначала
закрой риски, способные сделать остальную реализацию бесполезной: контракты,
границы модулей, корректность данных, совместимость и безопасность.

Если доступны несколько ИИ-агентов, можешь распределить независимые подзадачи,
но:
- назначай конкретного владельца каждой задаче;
- не допускай параллельной записи в один и тот же файл без координации;
- заморозь интерфейсы до параллельной разработки;
- требуй handoff с реальными тестами и commit hash;
- интегрируй результаты сам и запускай интеграционные тесты.

СТРОГОЕ ОСОБОЕ ПРАВИЛО: независимый verifier должен разрабатываться другим
человеческим владельцем/агент-контекстом, чем генератор. Не симулируй
независимость созданием двух модулей одним и тем же алгоритмом или импортом
кода генератора.

5. ПРАВИЛА РЕАЛИЗАЦИИ И КАЧЕСТВА КОДА
===============================================================================

5.1. Работай в рамках архитектуры
- Сохраняй разделение gen/, env/, verifier/, scoring/, harness/, seal/, arena/,
  judge/, contracts/ и docs/.
- Не смешивай публичные данные и приватный эталон.
- Не создавай циклические импорты и скрытые межмодульные зависимости.
- Не помещай бизнес-логику в CLI, отчёты или UI.
- Не дублируй одну и ту же логику без ясной причины и тестов.
- Не ломай публичные API и JSON schemas без одобренного CR.

5.2. Реализация
- Пиши production-quality код, а не псевдокод, заглушки, TODO вместо логики
  или фиктивные функции, возвращающие заранее известный успешный ответ.
- Используй type hints, понятные имена, небольшие функции и осмысленные ошибки.
- Обрабатывай граничные случаи и невалидный ввод.
- Не скрывай исключения широким `except Exception: pass`.
- Для внешних данных валидируй структуру на границе системы.
- Учитывай детерминизм сериализации, сортировки, RNG и хеширования.
- Не вводи зависимости без необходимости; core-ограничения Master ТЗ обязательны.
- Не подключай сеть, облачные API, внешние LLM или скачиваемые модели в core.
- Не добавляй реальные финансовые, банковские или персональные данные.

5.3. Деньги и даты
- Денежные значения — целые minor units.
- Курсы и промежуточные точные значения — Decimal, построенный из строки.
- Запрещено использовать binary float в денежной логике.
- Учитывай exponent валюты, режим округления и валюту функционального учёта.
- Время хранится в ISO-8601 с timezone offset.
- Периоды вычисляются согласно timezone и policy компании, а не по локальному
  времени машины.

5.4. Данные и доказательства
- Не создавай truth из одной лишь метки оператора без независимых проверок.
- Проверяй до/после инварианты и ожидаемые сигнатуры нарушений.
- Не требуй от policy факт, который нельзя получить публичными инструментами.
- Не делай free text единственной опорой для finding.
- Явно разделяй observed fact, derived fact, assumption и hidden metadata.
- Для каждого finding сохраняй трассируемую связь с доказательствами в приватном
  ProofGraph, не раскрывая этот граф policy.

5.5. Безопасность и sealed boundary
- Не выводи seed, truth, provenance, canary markers, приватные пути или секреты
  через observations, errors, logs policy или публичные отчёты.
- Не позволяй env импортировать sealed данные.
- Не позволяй policy напрямую обращаться к scorer, truth, verifier или generator.
- Не полагайся только на имя файла/директорию как на единственную защиту.
- Описывай фактическую силу процесса изоляции и ограничения платформы честно.
- Не публикуй приватные seed, salt до раскрытия, hidden labels и heldout truth.

5.6. Тестируй дефект, а не только счастливый путь
Добавляй проверки для:
- валидного сценария;
- неверного типа и структуры данных;
- пустых и граничных значений;
- дублирующих записей/запросов;
- некорректных ссылок и неизвестных ID;
- порядка данных и повторного запуска;
- ошибок бюджета, завершения и reset;
- атак и злоупотреблений, если они относятся к выбранной фазе;
- регрессий уже существующих фаз.

Не ослабляй тест ради прохождения. Если тест неверен, докажи это независимым
примером и зафиксируй решение с одобрением владельца.

6. ОБЯЗАТЕЛЬНЫЙ ЦИКЛ РАБОТЫ
===============================================================================

Выполняй цикл до закрытия всех задач выбранной фазы либо до конкретного
документированного блокера:

STEP A — DISCOVER
Прочитай контекст, осмотри код, подтвердить зависимости, зафиксируй baseline.

STEP B — SPECIFY
Сопоставь задачи фазы, REQ-ID, контракты, файлы, тесты и критерии приёмки.
Если не хватает деталей, выбери наименее рискованное совместимое решение и
запиши предположение. Не додумывай официальный контракт.

STEP C — IMPLEMENT
Внеси реальные изменения в нужные файлы. Работай небольшими логическими
порциями. Не останавливайся после написания плана или каркаса, если блокера нет.

STEP D — TEST LOCALLY
Запусти сначала узкие тесты изменённого модуля, затем все тесты соответствующей
зоны. Исправь реальные ошибки. Сохраняй точные команды и exit codes.

STEP E — REGRESSION
Запусти затронутые contract, integration, e2e, determinism, security, build и
performance checks, которые требуются выбранной фазой и доступны в проекте.

STEP F — REVIEW
Проведи собственный diff review:
- нет ли несвязанных изменений;
- нет ли случайного contract drift;
- нет ли секретов или приватных меток;
- нет ли недопустимых импортов;
- не нарушен ли детерминизм;
- не ослаблены ли тесты;
- обновлены ли схемы и документация при изменениях интерфейсов;
- не появился ли конфликт с предыдущими фазами.

STEP G — DOCUMENT
Обнови task cards, DECISIONS, STATUS, CURRENT_STATE, архитектурный snapshot,
phase report, agent report и NEXT_AGENT — по необходимости и фактическому
результату.

STEP H — GITHUB
Обнови соответствующие GitHub Issue/PR и приложи отчёт с результатами. Если
доступа к GitHub нет, сохрани файлы отчётов локально и поставь статус
PUBLISH_PENDING / REMOTE GITHUB UPDATE NOT DONE. Никогда не утверждай, что
удалённый GitHub обновлён, пока не получил реальное подтверждение и URL.

STEP I — COMMIT / HANDOFF
Сделай атомарный commit с релевантными REQ-ID и ссылкой на Issue, если это
разрешено правилами репозитория и рабочая ветка безопасна. Не делай force push.
Подготовь handoff с точным следующим действием.

STEP J — GATE
Проверь каждый пункт EXIT GATE выбранной фазы. Только после фактической проверки
присвой фазе DONE. Если хотя бы один обязательный пункт не выполнен, статус
PARTIAL или BLOCKED, с конкретной причиной.

7. СИСТЕМА ПРОВЕРОК И ПРАВИЛА ЗАЯВЛЕНИЙ
===============================================================================

Для каждого теста/команды фиксируй:
- точную команду;
- зачем запускалась;
- фактический exit code;
- PASS / FAIL / SKIPPED / NOT RUN;
- краткий фактический результат;
- путь к логу/артефакту;
- причину пропуска, если SKIPPED;
- последствия пропуска для EXIT GATE.

Запрещено:
- говорить «всё прошло», если запущена только часть тестов;
- называть SKIPPED статусом PASS;
- придумывать coverage, latency, AUC, reward, benchmark или количество тестов;
- писать «проверено на чистой машине», если этого не было;
- писать «GitHub обновлён», если удалённого обновления не было;
- заявлять безопасность, независимость или воспроизводимость по одному
  названию архитектуры, не имея тестов и доказательств.

Если обязательная команда отсутствует, не создавай фиктивный успешный wrapper.
Определи, какая реальная команда предусмотрена проектом, либо зафиксируй gap.
Если проверка недоступна из-за окружения, укажи это как BLOCKED или SKIPPED,
объясни последствия и предложи конкретный способ запуска в подходящем окружении.

Сравни результаты с baseline: отделяй старые ошибки от новых регрессий.

8. GITHUB-FIRST: ОБЯЗАТЕЛЬНАЯ ОТЧЁТНОСТЬ КАЖДОЙ ФАЗЫ
===============================================================================

GitHub и репозиторий являются постоянной памятью проекта; история диалога — нет.
Каждая рабочая сессия должна оставлять проверяемый след в файлах репозитория.

Минимально создай или обнови следующие артефакты (используй существующую
структуру, не дублируй её без необходимости):

1. docs/PHASE_REPORTS/PHASE-XX.md
   Полный отчёт выбранной фазы: цели, задачи, REQ-ID, изменения, проверки,
   EXIT GATE, дефекты, риски, GitHub links и готовность к следующей фазе.

2. docs/AGENT_REPORTS/YYYY-MM-DD/<agent>-phase-XX.md
   Отчёт этой рабочей сессии: контекст, базовый commit, итоговый commit,
   изменённые файлы, точные команды/exit codes, результаты, решения, проблемы.

3. docs/CURRENT_STATE.md
   Текущая ветка, HEAD, последний зелёный commit, текущая фаза, статус тестов,
   открытые блокеры, выполненные пункты и ровно три приоритетных next actions.

4. docs/STATUS.md
   Актуальная таблица статусов: PASS / FAIL / BLOCKED / NOT RUN / SKIPPED.

5. docs/CONTEXT/NEXT_AGENT.md
   Что следующему агенту читать, какие файлы смотреть, какие команды запускать,
   чего не менять и с какого конкретного действия продолжать.

6. docs/DECISIONS.md
   Новые архитектурные решения, допущения, отклонения и ссылки на CR.
   Не переписывай историю: документ ведётся append-only по правилам проекта.

7. Связанный GitHub Issue / PR
   Добавь summary, связанные REQ-ID, список файлов, тестовую таблицу, риски,
   ссылку на phase/agent report и commit/CI links. Не закрывай Issue, пока задача
   не удовлетворяет критериям DONE.

Имена файлов и каталогов можно адаптировать к уже принятой структуре репозитория,
но содержание и трассируемость обязательны.

В каждом отчёте обязательно укажи:
- Phase number / phase title;
- agent ID и human owner (если назначен);
- Master ТЗ version/hash;
- branch, start commit, end commit;
- Issue / PR / CI ссылки;
- REQ-ID и номера задач фазы;
- что уже существовало до сессии;
- что реализовано именно сейчас;
- файлы created / modified / deleted;
- контракты и API, которые затронуты;
- таблицу команд и результатов;
- failed/skipped/not-run checks;
- известные дефекты и ограничения;
- новые решения и допущения;
- EXIT GATE по пунктам;
- следующий конкретный шаг и его owner.

9. РАБОТА С GIT И ЗАЩИТА ЧУЖИХ ИЗМЕНЕНИЙ
===============================================================================

- Сохраняй существующие незакоммиченные изменения пользователя.
- Не переписывай чужие коммиты и не используй force push.
- Не делай массовое форматирование всего репозитория, если это не цель фазы.
- Не смешивай unrelated refactoring с обязательной реализацией.
- Сохраняй маленькие логические commits с REQ-ID.
- Перед commit проверь `git diff`, `git diff --check`, `git status` и staged diff.
- Не добавляй .env, credentials, private keys, local caches, hidden truth или
  временные артефакты, запрещённые спецификацией.
- Если commit не разрешён или невозможен, не скрывай это: оставь изменения
  локально, опиши причину и статус NOT COMMITTED.
- Удалённый push/PR выполняй только в корректный remote/branch и в пределах
  выданных прав. Не меняй protected branch напрямую.


===============================================================================
10. КРИТЕРИИ ЗАВЕРШЕНИЯ ВЫБРАННОЙ ФАЗЫ
===============================================================================

Фаза считается DONE ТОЛЬКО когда одновременно выполнено всё следующее:

A. Scope
- Все обязательные задачи выбранной фазы найдены и учтены.
- Все обязательные задачи либо реализованы и проверены, либо имеют явное
  обоснованное исключение, допускаемое Master/официальным ТЗ.
- Никакой неутверждённый feature creep не включён.

B. Correctness
- Реализация соответствует official contract и frozen schemas.
- Ключевые edge cases покрыты тестами.
- Не появилось регрессий в затронутых компонентах.
- Независимые границы модулей не нарушены.

C. Verification
- Все обязательные проверки выбранной фазы реально запущены и PASS.
- Нет неизвестных FAIL.
- SKIPPED не маскирует обязательное требование.
- EXIT GATE подтверждён конкретными артефактами.

D. Documentation
- Документация и контекст синхронизированы с реальным кодом.
- Phase report и agent report сохранены в репозитории.
- Следующий агент сможет продолжить работу без устных объяснений.

E. GitHub
- GitHub Issue/PR обновлён фактически либо выставлен честный
  PUBLISH_PENDING / REMOTE GITHUB UPDATE NOT DONE.
- Коммиты и CI-ссылки указаны только если они реально существуют.

Если любой блок A–E не закрыт, не присваивай DONE.
Используй:
- DONE — все обязательные пункты пройдены;
- PARTIAL — реализация продвинулась, но часть требований/проверок не завершена;
- BLOCKED — продолжение невозможно без внешнего решения, доступа или устранения
  конкретной блокирующей зависимости.


===============================================================================
11. ЧТО ДЕЛАТЬ, ЕСЛИ ВЫЯВЛЕНЫ БЛОКЕРЫ
===============================================================================

Не прекращай работу при первой проблеме. Сначала:
1. Установи точную первопричину.
2. Определи, находится ли исправление внутри scope выбранной фазы.
3. Проверь влияние на contracts и соседние модули.
4. Если исправление безопасно и входит в scope — исправь и добавь regression test.
5. Если нужен contract change — оформи CR, не обходи его.
6. Если не хватает официального ответа/секрета/доступа/внешнего решения —
   заверши независимые задачи и оставь конкретный BLOCKED пункт.
7. Для каждого блокера создай отдельный Issue или follow-up task с owner,
   impact, evidence и условием снятия.

Не подменяй реальную задачу упрощённым mock, фальшивыми данными или заглушкой,
которая делает тест зелёным, но не выполняет контракт.

Если времени/ресурсов не хватает, используй приоритеты Master ТЗ:
сначала обязательный уровень A, затем B, затем C. Не жертвуй correctness ядра
ради необязательных NLP/HTML/UI/Gymnasium enhancements.


===============================================================================
12. ФИНАЛЬНЫЙ ВЫХОД АГЕНТА — СТРОГО ПО ШАБЛОНУ
===============================================================================

В конце работы предоставь короткий, но точный отчёт в следующем формате:

PHASE: <номер> — <точное название из Master ТЗ>
STATUS: DONE / PARTIAL / BLOCKED

1. EXECUTIVE SUMMARY
Что было фактически завершено в рамках выбранной фазы.

2. REQUIREMENTS TRACEABILITY
Таблица: phase task → REQ-ID → status → evidence/artifact.

3. IMPLEMENTATION
Созданные/изменённые файлы и описание реального поведения.

4. TESTS AND GATES
Таблица:
| Command | Exit code | Status | Result | Log/artifact |
Не запускавшиеся проверки укажи как NOT RUN. Необязательные недоступные extras
пометь SKIPPED с объяснением. Покажи статус каждого пункта EXIT GATE.

5. GIT / GITHUB
Repository, branch, start/end commit, changed files, Issue, PR, CI, report links.
Явно отметь REMOTE GITHUB UPDATE DONE или REMOTE GITHUB UPDATE NOT DONE.

6. DECISIONS / DEVIATIONS
Новые decision IDs, CR, временные допущения и причины.

7. KNOWN ISSUES / RISKS
Все оставшиеся дефекты, ограничения, пропуски и влияние на проект.

8. NEXT PHASE READINESS
Можно ли начинать следующую фазу? Если да — какие обязательные входы готовы.
Если нет — назови точные блокеры и условия закрытия.

9. NEXT AGENT INSTRUCTION
Один однозначный следующий шаг, файлы для чтения, команда запуска и owner.

10. ARTIFACTS
Пути к phase report, agent report, handoff, logs и результатам проверки.

Не повторяй в финальном сообщении общие рекламные заявления о проекте. Сообщай
факты, конкретные доказательства и ограничения.
